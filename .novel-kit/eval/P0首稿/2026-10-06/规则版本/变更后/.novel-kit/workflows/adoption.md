# 开读冻结、版本采用与恢复

协调器执行本流程，写手只写候选，审阅者只读。Python 3.9+ 为必要依赖。命令在书稿根目录执行；作者无需手填 JSON、维护状态或操作命令。macOS 示例用 `./novel`，Windows 换为 `.\novel.cmd`，参数不变。

## 唯一状态与文件用途

- `追蹤/場景狀態.md` 是场景状态唯一入口，四栏由工具维护；新输出显示简体状态，兼容旧简繁输入，内部标识保留既有枚举。状态和备注版本不手改，不要求作者迁移历史。
- `草稿/第NNN章/場景MM.md` 是场景候选，采用后冻结；整章采用前读取最新有效场景及交付的章内事实增量。
- `草稿/第NNN章/整章候選.md` 是收尾候选；正式章仅由采用工具更新。
- `審閱/修訂/<id>/任務.json` 保存修订任务，不复制场景状态表。
- `審閱/採用/<id>/journal.json` 保存开读冻结、交付快照和恢复进度，不手改；reviewing 与 prepared 是同一日志的阶段，不新增第二份可编辑状态。
- 上下文清单、writer/blind 原文包是只读派生产物，记录来源与范围，不代替正式正文。

## 确认细纲与开始

作者明确确认后，细纲状态为单值 `- 状态：已确认`，场景标题为 `## 场景01 标题`，连续编号；旧繁体格式仍兼容。执行：

```sh
./novel confirm-plan 1
./novel begin 1 1
```

工具冻结细纲。尚未开始可改后重新确认；已有写作则需影响复核和 rebind-plan，不能手改摘要。收尾为场景号 0。

待审修改先 `reopen 1 1`（收尾为 0），旧交付失效。已采用内容走 revise，整章采用后修改最新正式章，不能修改旧场景再合并覆盖。

## 场景上下文供给

协调器按证据选必要前因，工具核对采用身份、生成同范围前文和来源清单，不自动理解语义。场景规格示例：

```json
{
  "chapter": 1,
  "scene": 3,
  "prerequisite_audit": {"status": "checked", "unresolved": []},
  "prerequisites": [
    {
      "path": "草稿/第001章/場景01.md",
      "start_line": 1,
      "end_line": 20,
      "reason": "本场涉及的物件来历，引用必要原文"
    }
  ]
}
```

```sh
python3 .novel-kit/scripts/context_packets.py 審閱/第001章/場景03_供给规格.json --output 審閱/第001章/場景03_上下文.json --root .
```

Windows 用本机可用 Python。必须显式给 prerequisites（无更早前因时为 []）及 prerequisite_audit；checked 是协调器选择记录，不证明实际充足，有未决项须先补核。输出清单与同源 `.blind.md`、`.writer.md`，三个目标都不得已存在，重做用新版本输出路径。直接前场自动取本章前一已采用场全文；跨章默认最新正式前章全文，以保守处理缺场景边界的导入。必要前因由 prerequisites 指定，只接受有效已采用来源，不以旧场景替代收尾后的正式章。累计事实从当前有效且明确绑定的交付读取，修订后替换失效增量；缺事实、空事实节或来源漂移标供给待核，无新增也须明确记录，不能凭空补造。

writer 包含同源前文与累计事实；blind 包只含同范围正文。前因理由保存在清单，仅协调器读取。写手另收创作护栏、细纲、贴近本场的已采用样本与作者已确认的修改理由（如有）。开读规格的 context 列出清单、两个原文包、清单 dependencies 及全部实际使用资料；context_ranges 使用清单 prose_ranges。copy-editor 不接收 writer 包、清单理由、写前准备、作者修改理由或设定，仅提供 blind 包、候选、语文规格与文风样本；补充规格仍只给裁决者。

## 审阅开始时冻结

候选完成、实际输入确定后，**先开读冻结，再启动审阅者**。例如协调器生成一次性规格 `審閱/第001章/場景01_v1.json`：

```json
{
  "id": "ch001-sc01-v1",
  "kind": "scene",
  "chapter": 1,
  "scene": 1,
  "files": [
    {"source": "草稿/第001章/場景01.md", "target": "草稿/第001章/場景01.md"}
  ],
  "context": ["設定/文風樣本.md", "追蹤/追蹤.md"],
  "context_ranges": []
}
```

示例 context 需换为本次全部实际输入及上下文清单依赖，不能照抄省掉前文。ID 用英数、底线或连字符。执行：

```sh
./novel review-start 審閱/第001章/場景01_v1.json
```

日志 version 2/status reviewing 保存精确输入。候选修正、补前文、上下文或范围变化后，用新 ID 和新规格重新开读；旧结果失效。每轮独立审阅读取对应冻结版本，不能审 A 后冻结 B。

## 详细交付与 prepare

完成审阅后，在同一规格补 delivery 和实际 review，不改 id、kind、目标或开读输入：

```json
{
  "delivery": "審閱/第001章/場景01_交付.md",
  "review": {
    "mode": "完整",
    "completed": ["copy-editor", "consistency-checker", "character-reviewer", "prose-reviewer", "structure-reviewer"],
    "unresolved": []
  }
}
```

completed 只填真正独立完成者；缺席、全部未决 S1/S2（含只建议不自动修者）、未改的确定性错误、严重分歧、关键待核或覆盖缺口写 unresolved。默认自动修资格按 review-loop 三类及证据、原意、事实与授权边界，不由严重度决定。其他别扭与文学建议、作者授权修改的执行情况及完整修改证据仍放交付；不能把减少自动修当成质量通过。

交付依 review-loop 逐场详细展示。**files 中每个 source 都须有唯一完整全文校验块**，包括追踪、兑现等候选。开标记后换行，嵌入源文件原始全文，保留源末尾换行，再加包裹换行和闭标记，例如：

```text
<!-- novel-candidate:草稿/第001章/場景01.md -->
〈此处逐字嵌入该 source 完整原文，保留其末尾换行〉

<!-- /novel-candidate -->
```

标记用于核对作者看到的文字和实际采用版本，不能用摘要、片段或“见文件”代替。协调器自动生成，不要求作者编辑标记。

```sh
./novel prepare 審閱/第001章/場景01_v1.json
```

prepare 同 ID 核对开读冻结及交付全文后改为待审。新 prepare 缺开读冻结会拒绝；之后候选、输入、交付或细纲变化须新 ID 重做。旧 version 1 prepared 不能首次采用，需重新冻结审阅；已 applying 的中断交易可按原机制恢复，complete 历史保留可读。

场景采用只更新该场，交付保留章内增量。收尾用 kind chapter、scene 0、mode 章節，映射整章候选到正式正文，必须同时包含最终追踪候选，另加所需兑现和设定。所有 source 都参与冻结和全文核对。正文和事实同步全部完成才算采用；内容正确性仍须审阅和作者判断。

## 作者采用

只有作者在对话明确采用该版本后执行：

```sh
./novel accept ch001-sc01-v1 --approval "作者回复：通过"
```

一个待审版本可由“通过”指向；多个须核对章、场、版本。approval 只是决策记录，不证明真人授权，不能捏造回复。必要审阅缺失或严重未决须记录作者针对缺口的明确裁决作为 override，不能把含糊认可扩张成全知。

排除变更先重做候选和交付，不采用包含排除项的快照。采用当前场后通常停止，通过并继续才推进下一场。末场采用后准备收尾交付。

## 撤回工作单元与细纲重新绑定

前置已采用正文漂移，或作者决定停止当前工作单元时，在明确授权下执行：

```sh
./novel withdraw 1 2 --reason "保留后场稿件，先修订前场" --approval "作者要求撤回当前工作单元并修订前场"
```

支持撰写中、自动审阅中、待审及对应无 journal 情况，收尾 scene 0。保留候选、作者手改和历史，使旧交付失效并退到未开始；中断可重跑。撤回不取消前置修订或版本检查，不能直接 begin 绕过事实同步。

已有写作后需改细纲：先撤回正在工作单元，完成必要依赖修订和复核，作者明确确认新细纲及影响范围后执行：

```sh
./novel rebind-plan 1 --reason "作者确认新细纲，相关已采用内容已复核" --approval "作者确认本次细纲版本与影响复核"
```

要求无正在稿、未完成修订或待复核，既有采用正文仍与有效版本一致。保留已采用场景 ID，可新增未开始 ID；不得删除已开始场景。语义重编号或改变已采用场含义先分析，不把工具结构检查冒充故事复核。

## 修订与逐场确认

文字与情节修订都建立任务：

```sh
./novel revision-start fix-ch001 正文/第001章.md
```

目标必须是有采用依据的正式章、已确认导入章或已采用场景，不能把未开始文件借修订通道采用。当前快照是开始审阅时的稿；作者已手改时，改前依据另取采用 journal 或核实 Git，找不到明示。

整章按场景逐一优化、完整展示和等待作者确认；分场确认只确认对应候选，不将截取片段映射到整章。全部场景确认后合成完整目标，执行整章独立盲读，以 kind revision、revision 指向任务、files 映射完整目标候选。文字修订用文字模式，情节修订用完整模式；最终跨场检查按 review-loop。同样先 review-start，再审阅、交付全文块、prepare、等待完整目标采用。

每次只正式采用一个完整正文目标；追踪变更到修订收尾。同章前场修订后，后续已采用内容标待复核，依原文证据和作者授权用 revision-extend 纳入；不用改字的依赖也可用相同完整候选复核。跨章依赖由一致性审阅搜索，脚本不理解情节因果。

任务中作者再次手改：

```sh
./novel revision-refresh fix-ch001 正文/第001章.md --reason "作者再次手改，要求只审当前稿"
```

保留各次基准、采用历史和当前稿，将该目标改为未采用，不修改正文。旧待审版本失效，新 ID 重审；其他目标进度保留。不能用 refresh 绕过 applying/reverting，先恢复交易。

全部正文目标采用后，kind revision-finish、同 revision，files 至少包含最终追踪，另加所需设定与兑现；先冻结、审阅、交付、prepare，再等作者采用。收尾完成才解除续写阻塞。未采用且目标未手改可 revision-cancel；部分采用或已 refresh 不能直接取消。

## 中断、提交与 Hook

accept 中断重跑原 ID；工具先核对所有目标再跳过已完成者。外部手改冲突停止并保留现场，不能强制覆盖。放弃中断用 rollback --reason，仅恢复仍为冻结改前/改后版本的文件；complete 采用走修订，不 rollback。prepare 中断保留日志，依实际状态恢复或新 ID 重交付。

Git 可选，只列本次实际路径：

```sh
./novel commit --message "第001章 场景01 通过" 草稿/第001章/場景01.md 追蹤/場景狀態.md 審閱/第001章/場景01_交付.md 審閱/第001章/場景01_v1.json 審閱/採用/ch001-sc01-v1/journal.json
```

路径按字面文件名处理。有原有暂存变更时保留采用、停止自动提交；禁止 git add -A，不混入或清掉暂存。失败报告“已采用、未提交”。

启用 Hook 检查 Write/Edit/MultiEdit/NotebookEdit/apply_patch（含移动两端），正式正文和工具专属状态、采用日志、修订任务、导入清单禁止直接写。书稿外绝对路径只有字面、真实路径和文件身份均在外才放行；别名回到书稿照常检查。非法 Windows 路径、数据流、末尾点空白拒绝。

找不到有效 Python 时，以上匹配写入工具全部拒绝，含普通设定和书稿外路径；只读工具可用。修复运行环境后 doctor，不用路径回退猜测保护身份。Shell、外部编辑器、其他 MCP 写入和未匹配工具不在 Hook 拦截范围，版本核对发现漂移但不证明真人授权。未启用或未信任 Hook 时，候选写前自行 check，正式采用仍走工具。完整边界见 docs/compatibility.md。
