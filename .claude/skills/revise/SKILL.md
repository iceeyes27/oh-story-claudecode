# 修改正文

依 `.claude/workflows/adoption.md` 操作候選和修訂任務，依 `.claude/workflows/review-loop.md` 審閱。

## 範圍與基準

- 已收尾的章節修訂 `正文/第NNN章.md`；尚未收尾的已採用場景可修訂場景草稿。
- 待審稿走 write-scene 的修改流程。有正在撰寫或待審的場景時先完成該交付。
- AI 修改：依作者已給出的範圍與要求，不重複詢問已明確授權的內容。
- 作者手改：保留當前作者稿；以已核實的上次採用快照或 Git 版本比對，沒有基準則明示缺失，不把當前作者稿當成改前稿。

只改表達、不改事實、知情、關係、設定或兌現的是文字修訂；其他是情節修訂，分不清時按情節處理。

## 情節影響分析

列改前與改後事實，讓 consistency-checker 搜尋後續正式正文及同章已採用場景。區分必須改、可能改，附原文位置；列受影響的伏筆、知情、設定與兌現證據。只對尚未授權的新增範圍請作者決定，不順便擴大修改。

## 建立任務與逐項交付

文字與情節修訂都執行 `revision-start <id> <目標檔案...>`，保存當前稿、阻止續寫。不先 commit 全工作區。

將目標複製為 `審閱/修訂/<id>/` 內的候選。scene-writer 模式六只修改候選，正式正文只讀。每次處理一個目標：

1. 先掃描候選；文字修訂用文字模式，情節修訂用完整模式；審閱整個目標。修訂稿同樣要求簡體正文，作者禁詞與繁體字列為問題。
2. copy-editor 讀前章末與後章首各約 1500 字，場景則用相鄰場景；需要時擴充原文範圍。
3. structure-reviewer 的依據是作者修改要求和原細綱（如有）。
4. 作者手改不呼叫寫手、不自動修；所有問題（含掃描命中）列給作者，僅依後續明確指示修改。
5. 交付改前/改後對照、閱讀範圍、未決問題與保留項，以 revision 類型 prepare。停下等作者採用。
6. accept 只採用這個目標，任務仍進行中；再處理下一個已授權目標。提交依檔案白名單，不動原有暫存。

同章場景修訂會將後續已採用場景標為待復核。依影響證據及作者範圍使用 revision-extend；無需改字的依賴可用相同正文候選復核採用。跨章依賴由審閱搜尋，不宣稱腳本能判斷故事因果。

## 全部修訂收尾

全部目標採用後，重新判定受影響兌現；舊證據消失即退回待核或適當狀態，附理由。生成最終追蹤、設定、兌現登記的候選，寫明修改事實與各章狀態。

以 revision-finish 類型交付，至少包含最終追蹤。作者採用這份收尾後任務才完成；不能在最後一章通過時提前解除續寫阻塞。取消、中斷恢復和按檔案提交依 adoption 流程。
