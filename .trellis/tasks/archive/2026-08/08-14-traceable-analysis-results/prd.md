# 可追溯分析结果层

## Goal

在不改变现有 Skill + Markdown 体系的前提下，为 `story-analyze long` 增加可验证的分析运行记录和关系结果版本，使中断恢复、重试、证据核查和结果变更都有机器可读依据。

## Background

- 现有 `_progress.md` schema v3 已固定原文 SHA-256 与唯一章节边界，并且 Stage 2 已有失败章节和重试流程。
- 现有 Stage 4c 会产出角色关系与演变轨迹，但缺少独立的结果修订号、证据文件指纹和统一的关系端点规则。
- 目标项目值得吸收的是原文版本、分片状态、不可变结果集、证据区间和别名归一概念，而不是其 FastAPI / React / SQLite 运行栈。

## Requirements

### R1. 分析清单

- `story-analyze long` 在 Stage 0.5 章节边界验证后初始化 `拆文库/{书名}/_analysis-manifest.json`。
- 清单必须绑定 `_progress.md` 中的原文路径、字节数、SHA-256 和章节边界摘要。
- 初始化可重复执行；相同输入不重置进度，不同输入必须拒绝。

### R2. Stage 2 章节尝试与恢复

- 每章有稳定的输入指纹和追加式尝试记录。
- 成功尝试必须绑定实际输出文件的相对路径与 SHA-256；失败尝试必须包含错误摘要。
- 恢复查询只返回未处理或最新尝试失败的章节，已成功章节不重复处理。
- Stage 2 存在待处理章节时不能完成；失败章节默认阻止完成，但可显式标记为 `completed_with_errors` 后继续现有管道，并保留后续恢复重试能力。

### R3. 关系结果版本与证据

- Stage 4c 可将结构化草稿发布为 `_analysis/results/relationships-vNNNN.json`。
- 结果版本连续增长，清单记录当前修订号、文件路径、内容指纹和数量摘要；相同规范化内容重复发布时不创建新版本。
- 证据必须指向拆文目录内的普通文件，并记录文件 SHA-256、行区间和区间 SHA-256。
- 证据越界、符号链接逃出、空区间或文件改变必须被验证器拒绝。

### R4. 关系规范化

- 只有 `proper_name` / `nickname` 且置信度不低于 0.85 的别名可归入主实体。
- 无向关系按实体 ID 统一端点顺序；有向关系保留方向。
- 别名归一后的自环、未知实体、重复实体/别名和重复关系键必须拒绝，不得静默丢弃。
- 实体与关系置信度必须在 0..1 之间，每条关系至少有一条证据。

### R5. 契约与兼容

- 新契约的 schema 版本纳入 `scripts/current-contract.json` 和当前契约检查器。
- `story-analyze` 文档必须说明初始化、记录尝试、恢复查询、Stage 2 完成和 Stage 4c 发布步骤。
- 存量拆文库没有新清单时不作废；从下一次 Stage 0/2/4c 执行时初始化。
- 不增加 CI / GitHub Actions，不引入第三方运行依赖，不引入后端服务或数据库。

## Acceptance Criteria

- [x] AC1: 有效 schema v3 `_progress.md` 可初始化并验证 schema v1 分析清单，重复初始化不改变既有运行历史。
- [x] AC2: 原文、章节边界或清单内部结构被篡改时验证失败。
- [x] AC3: Stage 2 尝试历史、成功输出指纹、失败错误和待恢复章节可被稳定查询；显式保留失败时状态为 `completed_with_errors`。
- [x] AC4: 含别名、有向/无向关系和证据行区间的草稿可发布为不可变结果版本，且相同内容可去重。
- [x] AC5: 自环、非法别名、未知实体、重复关系、非法置信度、缺失/越界/改变的证据都有回归测试。
- [x] AC6: 新 schema 版本与文档流程由当前契约检查器防止漂移。
- [x] AC7: 相关 Node 单元测试、当前契约测试、静态检查和 `git diff --check` 全部通过。

## Out of Scope

- FastAPI、React、SQLite、G6 图谱、独立模型配置和 API 认证。
- 将存量 Markdown 拆文产物批量转换为新结构化结果。
- Dashboard 专用关系图可视化；新 JSON 仍可通过现有工作台浏览。
