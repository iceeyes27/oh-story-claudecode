# 修改正文

原則：**先確認範圍，再動手；每一章各自通過；只改授權範圍。**

## 一、確認範圍與方式

1. 確認修改對象：
   - 已定稿章節：`正文/第NNN章.md`
   - 本章進行中、已通過的場景：`草稿/第NNN章/場景MM.md`（修改後本章收尾時會重新合併）
   - 還在「待審」的場景不走本流程，直接用「修改：」回覆。
2. 確認方式：
   - **AI 修改**：使用者給出範圍與要求
   - **作者手改**：使用者已自己修改。專案是 git repo 時，用 `git diff` 找出改動；不是的話，請使用者指出改了哪些段落
3. 建立修訂資料夾 `審閱/修訂/〈日期〉_〈簡短名稱〉/`，本次所有紀錄都放這裡。

## 二、分類

- **文字修訂**：只改表達，不改任何事件、事實、角色知情、關係、設定、兌現。
- **情節修訂**：只要改變了上述任何一項，或新增、刪除了場景內容，就屬於情節修訂。

**無法確定時，一律當成情節修訂。** 在對話中告訴使用者分類結果與理由。

## 三、影響分析（僅情節修訂）

1. 整理出「將被改變的事實」清單（改前 → 改後）。
2. 呼叫 `consistency-checker`（影響分析模式），給它這份清單、修改範圍之後的所有章節、`追蹤/`、`設定/兌現登記.md`。
3. 寫入 `影響分析.md`：
   - 必須跟著改的章節與位置（附原文）
   - 可能要改的位置（附原文與理由）
   - 受影響的伏筆、角色知情、兌現條目（特別是證據落在修改範圍內的「已兌現」條目）
   - 需要跟著調整的設定
4. **停下，請使用者確認處理範圍**：哪些章節要改、哪些保留、設定要不要跟著調整。沒有確認就不得修改任何正文。
5. 使用者確認後，在 `追蹤/場景狀態.md` 新增一列 `| 第NNN章 | 修訂 | 修訂中 | 〈修訂名稱〉 |`（每個要改的章節一列）。**有任何「修訂中」時，不得開始寫新場景。**

## 四、修改前的基準

專案是 git repo 時，先 commit 目前狀態（「修訂前基準：〈名稱〉」），確保可以回復。

## 五、逐章修改與審閱

依章節順序，一次處理一章：

**AI 修改：**

1. 呼叫 `scene-writer`（模式六：修訂），給它正文路徑、修改範圍、修改要求、已確認的影響範圍，以及相關的設定、角色卡、追蹤。
2. 依 `.claude/workflows/review-loop.md` 審閱：
   - 情節修訂用**完整模式**；文字修訂用**文字模式**
   - 審閱對象是整章，不是只有修改的段落
   - copy-editor 的前文是上一章最後約 1500 字，**另外給下一章開頭約 1500 字**，檢查兩端的銜接
   - structure-reviewer 的依據是修改要求與原細綱（有的話）

**作者手改：**

1. 不呼叫寫手，直接依 review-loop 審閱作者的修改，範圍與上面相同。
2. **不自動修正作者寫的文字。** 所有問題只列在交付檔，由作者決定要不要讓 AI 修（例如回覆「修 CE-2、CC-1」），或自己改。
3. 修改涉及情節時，照第三節補做影響分析。

**交付：** 寫入修訂資料夾的 `第NNN章_交付.md`。格式同 review-loop 的交付檔，但第一節改為「修改對照」：逐段列出改前與改後，不必貼全文（除非改動超過全章一半）。停下等使用者回覆。

**通過後：** 該章的「修訂」列改為「已通過」，git commit，然後處理下一章。

## 六、全部完成後

1. 依最終版本更新 `追蹤/追蹤.md`。
2. 重新判定受影響的兌現條目：呼叫 `structure-reviewer`（模式一）對證據所在段落做兌現判定。原本「已兌現」的條目可能退回「部分兌現」或「已排入」，照實更新並寫明原因。
3. 設定有調整的，更新 `設定/` 並在變更處註明修訂名稱。
4. 在修訂資料夾寫 `總結.md`：修改了哪些章節、改變了哪些事實、登記表的變化。
5. git commit（「修訂完成：〈名稱〉」）。
