# 设定完善与兑现流程

本文件是长篇设定流程的权威协议。编排器在 Phase 2 设定完成、Phase 3 每个剧情单元建纲、Phase 4 写前、Phase 5 候选复核、采用/修订及卷末按对应段执行。不要把全文交给普通写手。

## 1. 完善性关卡：设定能否支撑接下来的剧情

架构师读取本书设定与当前单元计划，交由一致性复核方核查；没有可用 agent 时主会话独立执行复核并标明 solo。这是一轮语义检查，脚本不代替判断，也不能把签名当作人类认可。

必须给以下六个维度逐项结论，引用具体规则或说明缺失内容：

| id | 核查内容 |
|---|---|
| rules | 适用条件、效果、限制、例外和反制是否明确；是否有直接冲突或能绕过核心矛盾的漏洞。无成本能力可以成立，不硬造代价 |
| resources | 金钱、时间、距离、能量、库存的单位和数量是否一致；依照本批事件核算收支、恢复和升级门槛 |
| characters | 主角与关键对手的目标、动机、知识、能力和行动边界，是否足够解释本单元的选择 |
| information | 作者真相、人物所知、读者已知是否分开；关键转折的必要前因应在哪章进入正文 |
| progression | 新能力、身份、关系的获得条件和阶段是否统一；当前剧情需要的角色、地点、规则是否已有来源 |
| closure | 核心承诺最终交付什么、付出或承担什么、在哪个卷/单元收口；远期可以保留到期再定的问题，不要求开书就写完全书细纲 |

审查产出 `设定/_设定审查.json`，不另造一套设定真相。`sources` 记录 `设定/` 内所有非隐藏 Markdown 文件（包括登记表）的相对路径和 SHA-256；来源新增、删除或修改后，复核影响面再更新记录，禁止仅重算哈希盖章。可用 `_shared/scripts/setting-readiness.js` 导出的 `sources(bookRoot)` 获取文件清单与哈希；它不会生成审查结论。

```json
{
  "schema": "setting-readiness/v1",
  "reviewer": "实际复核方；独立 agent 或主会话 solo",
  "sources": {"设定/世界观.md": "文件实际SHA256", "设定/_设定登记.md": "文件实际SHA256"},
  "checks": [
    {"id":"rules","status":"ready","reason":"具体前提与边界的核对依据"},
    {"id":"resources","status":"ready","reason":"本单元预算核算依据"},
    {"id":"characters","status":"ready","reason":"角色选择依据"},
    {"id":"information","status":"ready","reason":"真相、知情范围与披露安排"},
    {"id":"progression","status":"ready","reason":"进阶与供给核对依据"},
    {"id":"closure","status":"open","reason":"远期结局保留一个明确待定问题"}
  ],
  "issues": [{
    "dimension":"closure", "severity":"blocking", "problem":"终局选择的结果未定",
    "from_chapter":80, "to_chapter":null, "return_to":"outline",
    "next_action":"第80章建纲前确定选择、结果和承诺收口"
  }]
}
```

`status` 只允许 `ready/open/not_applicable`，均需具体理由。`open` 必须关联 `issues`。问题写受影响章范围，`to_chapter:null` 表示以后全部；全局硬冲突从第1章起。未来缺口不阻断无关章节，但不能把影响当前剧情的问题移到未来。解决问题时更新来源和结论并移除该未解决项，决策理由保留在相关设定/单元的变更说明。脚本只能保证审查记录齐全、未过期、受影响问题被拦截，无法证明审查结论真实。

## 2. 登记与规划：哪些需要呈现，哪些必须遵守

唯一规划登记表是 `设定/_设定登记.md`。编号只增不重用，不绑定文件名数字。以有意义的叙事义务登记，不把每个名词都变成展示任务。

| 类型 | 用途 | 排期规则 |
|---|---|---|
| payoff | 承诺读者理解或看到的能力、结果、人物表现 | 写目标章/章区间；远期可先写卷，在该卷细纲形成前细化成章 |
| constraint | 能力边界、行为规则、资源预算等 | 写触发条件；只要适用就遵守，不必每次解释 |
| recurring | 应持续感受到的人物特征、关系或氛围 | 按本书节奏写每 N–M 章窗口；超窗复核，不强行重复同一句话 |
| reserve | 暂不进入正文的储备 | 写预期启用阶段；启用前转类型并补规则与目标 |
| retired | 明确取消的规划 | 保留原编号及放弃理由，不删除历史事实 |

```markdown
| 编号 | 类型 | 来源 | 一句话 | 触发条件 / 窗口 | 兑现目标（读者要理解什么） | 摘录锚点 |
|---|---|---|---|---|---|---|
| SET-001 | payoff | 设定/能力.md#留影 | 录音取证 | 第1–3章 | 读者看到录音改变对方的选择 | 能当面回放 |
| SET-002 | constraint | 设定/能力.md#耗电 | 使用耗电 | 每次扫描 | 不能超出现有电量使用 | 扫描消耗两格电 |
```

来源与摘录必须真实存在。写前启用关卡不接受 payoff 缺目标、recurring 缺有效窗口、payoff/constraint 缺摘录或活动条目缺目标。登记表新增和更改后回完善性关卡复核影响面。

每个剧情单元的供给自查增加「设定供给」：本单元使用/兑现哪些编号、当前缺口、延期或退役的理由和影响。B 级发明先落设定，判断所属类型并登记；C 级按原流程交作者裁定，其他不受影响部分继续。具名实体扫描只是漏项提示，复核为储备/组合概念/真实漏排后处理，不以所有名词上台作为完成标准。

## 3. 细纲与骨架：写手不负责补规划漏洞

细纲用下列小节。没有相关设定时写一行 `无`。一个编号一行。

```markdown
#### 设定兑现
| 编号 | 关系 | 本章呈现目标 | 备注 |
|---|---|---|---|
| SET-001 | 兑现 | 当面播放录音，使对方无法继续否认 | 主场景：柜台交涉；结果：退还押金 |
| SET-002 | 涉及 | 扫描后电量下降，与预算一致 | |
```

关系为 `兑现/涉及/不适用`；不适用必须写原因，且只描述本章，不取消全书义务。规划具体的选择、阻碍、行动、结果及必要理解，避免把定义换一种说法当成场景。表现形式按内容选，不要求物证/动作/台词齐备，不强制每条有梗。

骨架把需兑现编号绑定到主场景，保证事件因果可展开；constraint 在相关场景核对边界。写手任务由 `build_writer_prompt.py` 组装本章目标、相关规则摘录、已发生事实及允许自由发挥的范围。写手保留台词、节奏、细节创造权；新增硬规则或改动既定结果时返回设定/细纲，不在正文里临时发明补洞。

## 4. 写前执行与兼容

新长篇在 Phase 2 建登记表、完成审查，在追踪初始化时启用 `setting_payoff: {"enabled":true,"schema_version":1,"since_chapter":1}`。Phase 3 确定本章排期后运行：

```text
node .agents/skills/_shared/scripts/check-setting-payoff.js <书目录> --json --chapter N --readiness
```

exit 1 返回点名的设定/细纲层处理，exit 2 修复运行错误；不可继续组装写手任务或伪称跳过等于通过。最多两轮定向返修后仍不通过，报告未解决问题与返回阶段，保留产物，不强行生成正文。

旧书无登记表时维持兼容；这叫未启用，不叫验收通过。已有旧看板的迁移步骤：备份后运行检查器 `--migrate`，复核分类、来源摘录、真实窗口和目标（迁移生成的空项不可直接放行），完成审查记录，再运行 `tracking_commit.py enable-setting-payoff --project <书目录> --since-chapter N`。只从指定新章开始记账，不伪造旧正文证据。迁移或继续使用旧机制须如实报告状态；本协议不会自动改写已采用正文。

## 5. 写后复核：证据存在不等于已经兑现

编排器依次执行：

1. 机械检查登记、细纲、骨架和证据对应关系。
2. 一致性复核方比对规则、正文证据和事件结果：是否真的呈现目标、是否违反规则；不接受只出现名词或复制定义。叙述解释是否过量结合读者需求判断，不将所有解释句判违规。
3. 读者复核只读此前已采用正文与本章候选，不能看设定/细纲/追踪；报告关键事件能否理解、是否缺前因、设定是否通过事件产生效果。可复用 reader-comprehension-scan；无独立 agent 时标 solo，不冒称独立或人类读者。
4. 每个问题给证据、影响和返回层：规则矛盾→设定；排了但无戏可演→细纲/骨架；表达不清或证据缺失→正文。沿既有候选流程做定向返修与重验，作者采用前不推进正式追踪。

候选事务 `candidate_binding.setting_payoffs` 每条包含 `id`、`registry_sha256`、`relation`、`evidence:[{"anchor":"正文原句"}]`、`review:{"result":"已兑现","note":"具体语义判断依据","reviewer":"实际复核方"}`。本章无条目时为 `[]`。关系与细纲一致，证据可用多个短段。

结论按候选脚本现有枚举：兑现→已兑现/部分兑现/未兑现；涉及→已遵守/违反；不适用→条件未触发。违反不能采用。部分/未兑现要在 note 写已完成和剩余内容，并给下一目标；条件未触发写原因。**这些结论均不等于全书义务销账。** 脚本验证原句、绑定与记录，不自行判断文学质量；语义复核和作者采用仍是不同层面的证据。

## 6. 采用、修订与卷末

采用时 `candidate-commit.py` 生成 `delta.setting_payoff_changes`，随已有追踪事务提交；不要手填该 delta，不直接改 `_tracking-state.json`。正式事实保存在 `setting_payoffs`，`追踪/设定兑现.md` 是派生视图；旧看板退役。所有长篇成稿路径共用候选采用流程，不留批量直写绕过路径。

普通修订走 `revision-commit.py`：证据句消失须重新绑定；若实际事件或兑现结论变了，转事实修订而不是只换证据句。失败或中断按既有 recover/abort 恢复，不手改状态掩盖问题。

卷末审计追查截至本卷的历史未清义务，只有 `已兑现` 算完成；`部分兑现/未兑现/条件未触发` 保留义务。延期须在登记表保留理由并更新目标章，再更新审查记录；放弃须转 retired 并保留理由，不能删除或虚报完成。卷级目标必须在该卷建纲时细化成章，不能无限停在“以后再说”。作者批准延期后仍须先更新登记和审查记录；通用 `volume_gate` 批准不代替这些操作。已完成条目的目标若发生实质变化，新增义务编号或走事实修订重新复核，不能借旧证据结清新承诺。

贯穿窗口按距离上次实际兑现的章数判断：每1–2章，若第1章兑现，第3章处于上界，第4章才超窗。条件未触发不重置窗口；从启用章起累计，跨卷不清零。超窗是需要语义复核的提示，不自动要求补口癖。

## 7. 验收证据

基础检查、完整采用/修订链路、读者语义复核和作者采用分别报告，不合并成“书已写好”。至少验证：正常通过、遗漏审查、来源变更、当章阻断/未来缺口、遗漏排期、约束违反、假证据、部分兑现不销账、跨卷旧债、延期、修订证据失效、失败恢复。适配入口检查通过仅证明平台读取一致。
