# 读者视角理解力扫描（只读正文，读者看不看得懂）

现有一致性检查都是**作者视角**——拿正文比对 `设定/`、`追踪/_tracking-state.json`、细纲。但设定里自洽 ≠ 正文里交代过。读者手上只有已发布正文，弃书弃在「正文没说清楚」，不在「设定没写」。本 skill 专补这个缺口。

## 立身铁律：只读正文

**执行本检查时只读正文，绝不读 `设定/`、`大纲/`、`追踪/`、`对标/` 或设计卡。** 通常读取已采用的 `正文/`；候选检查另含当前候选正文，不含其他版本。每批最多 5 章是必需精读窗口；针对第 N 章允许向前检索已采用正文并回查上下文，禁止读取未来章为当前判断补答案。同批也按章序记录当时理解。独立审读者不得参与本批创作/规划；父流程不注入意图或预设答案，见 [references/reading-protocol.md](references/reading-protocol.md)。

## 两层检查

### 第 1 层：专名首现交代（确定性脚本）

```bash
node ../_shared/scripts/check-first-mention.js <书目录> [--json] [--min-freq=3] [--reintro-gap=2] [--known=<文件>]
```

- 只报**高精度信号**：① 书名号/引号具名实体（作品名/道具名/绰号）；② 命中虚构专名尾字白名单的 token（系统/阁/宗/令/诀…，白名单在脚本顶部 `NAME_SUFFIX`，按题材增删）。
- **人名/机构不由脚本猜**——中文没有分词，硬猜会把「说道/办公室」全当专名。人名的理解断点交给第 2 层语义通读。
- 裸串候选以量词开头（`MEASURE_PREFIX`）一律丢弃：n-gram 会把量词粘进来，「获得了一个系统」切出「个系统」这种残留会误导作者。数词不在过滤列表内——`三清殿`、`九幽阁`、`万剑宗` 是真专名，滤掉就漏报了。
- **现实世界实体要声明**：脚本分不清《如愿》是真实歌曲还是虚构曲目。真实歌曲、影视、历史人物对读者本就已知，正文不交代不构成理解断点。在 `正文/_已知实体.txt` 每行写一个（`#` 开头为注释）即自动生效，或用 `--known=<文件>` 指定。这是**作者一次性声明**，脚本不猜。
- 严重度：默认 advisory；「首现零交代 + 之后 ≥2 章再被当已知前提出现」升 blocking（读者被要求记住一个从没解释过的东西）。退出码 0/1/2。
- 输出的每一处是**定位线索**，需人工核对首现处是否真的缺交代（也可能交代在别处、或角色本就该神秘）。

### 第 2 层：六问连读（语义层，召回主力）

脚本只覆盖可机械判定的子集，人名/因果/信息差/空间逻辑/道具物理流转/金融常识的召回靠语义通读。按 [references/reading-protocol.md](references/reading-protocol.md) 分批派**只读正文**的子代理，对每章逐问：

1. 这章谁在做什么？（正文本身能不能说清）
2. 为什么做——前因在**本章或此前正文哪一章**交代过？指不到先向前检索、回查；只报告在已核查范围内未找到，证据不足归入待核实。明确暗示可以成立，不强求旁白明说。
3. 读者读到这里，手上信息够不够理解本章的关键转折？（不够 = 理解断点）
4. 本场景在场人物与空间关系是否自洽？（空间在场与群演人数守恒：严禁前脚刚口头/写纸条交代“去某处找某人”，后脚同一封闭房间内突然写“某人的伙计/手下一直站在角落”；严禁单人进门、中途凭空冒出后生、退场时凭空分裂成“两个后生”的无交代瞬移穿帮）
5. 关键道具与凭证的物理持有权是否连续？（道具持有权连续性：关键凭证如借据、契约、存折、信物在各章流转必须有物理交代；前文已明确交代被角色 A 收入贴身怀里的道具，后续章节绝不能在无转交描写的情况下凭空被角色 B 掏出来交付）
6. 金融票据实务与货币购买力/物理体积是否自洽？（金融票据与购买力自洽：银行本票/汇票属于单张不可分拆的有价证券，严禁写成“切下一角取现、剩下的本票重新塞回匣子盖印”；现金散钞必须遵守物理体积与历史购买力常识，严禁用“一封纸包抱怀里”承载成千上万张散钞，严禁出现用足以买下一艘大渔船三分之一的数千万盾巨款去平几升米钱几副药账等底层物价数量级崩塌）
7. 信息冗余与多嘴解释：角色对话或旁白是否在重复、解释读者已经亲眼看到/亲耳听到的事？（冗余检查：AI 已经开口叫了“老板”，又补一句“叫您老板是默认称呼”——读者亲耳听见的称呼，再用台词解释一遍是废话；同理，刚展示过的动作、刚念出的数字、刚发生的反应，不要再由任何角色复述一遍当说明。与“信息不足”相反，这是信息过剩。判例：《霍格沃茨》第1章“本机是离线助手，叫您老板是默认称呼”删掉后半句。）另查叙述主语是否半句漂移：前半句说 A（这声音他熟），后半句直接跳 B（连称呼型号都是他设的）却没有连接词，读者会问“手机出厂声线凭什么他熟”——凡出现“他一听就懂/他太熟了/他一眼就认”这类瞬间判断，必须核：这个判断的依据前文给过吗？没给就补上因果，别让读者替作者脑补。

任一问存在疑点先核查，再区分确认断点与待核实；未查证、预算耗尽或外部专业事实不明不能直接定错。记录章节、当前原句、前文依据或回查范围及影响。前文已充分交代则不要求补重复解释。

## 工作流程

1. 确认扫描目标：默认当前书 `正文/` 全卷。
2. 第 1 层跑 `check-first-mention.js`，blocking 逐条 Read 首现上下文复核。
3. 第 2 层按 reading-protocol.md 分批通读，穷举理解断点。
4. 父流程逐项核对跨批前因：按 reading-protocol.md 安排前文回查及消歧，分「确认断点 / 待核实 / 前文已交代」，附原始 `章节:行号`、实际精读/检索/回查范围、文本版本和证据。未读或未独立审读单列；不得把检索全目录算通读全书。
5. **默认 report-only**，不擅自改正文；用户要改时再逐处 Edit。

## 能力边界

第 1 层脚本通过只表示「已知高精度首现模式未发现 blocking」；第 2 层依赖模型语感，覆盖率不保证穷尽。两层都通过**不能**据此声称「读者一定看得懂」。这是辅助定位工具，最终由作者读者审读判断。

## 与其它检查的关系

- `story-review`：作者视角一致性（比对设定/追踪）。本 skill 是读者视角，两者互补不重叠。
- `outline-causal-fields`（细纲前因字段）：在写前建因果；本 skill 在写后查因果是否落到正文。
- 语言：跟随用户语言回复；中文遵循《中文文案排版指北》。
