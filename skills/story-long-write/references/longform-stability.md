# longform-stability.md：长篇稳定性验收

把长篇连载的稳定性约束从"靠模型自觉遵守 prompt"升级成"落盘工件 + 确定性脚本验收"。核心闭环：**写前立契约（细纲稳定性小节）→ 写后过门控（漂移门控落盘）→ 门控通过才交接（交接包）→ 批量脚本验收（稳定性审计）→ 失败按错误码分派修复，直到 PASS**。

设计哲学与 `check-ai-patterns.js` / `check-degeneration.js` 一致：脚本不做语义判断，它验证的是"模型有没有把承诺落盘"和"落盘承诺与正文是否字面一致"。语义审查仍由模型做，但结论必须写成机器可验的格式，修复闭环才能自动化。

## 启用条件（正文超过 10 章自动启用）

满足任一即启用「长篇稳定性验收」：

1. **`正文/` 已有章节数 > 10 —— 自动启用，不询问用户**。判定时机在写前：单章流程步骤 1 检查细纲时、日更 Step 1 确定章号时，数一次 `正文/` 章节数；首次越线先执行下方「首次启用初始化」，再继续写作。质量优先于 token 成本：长篇写崩重写的浪费远大于每章一轮门控审查。
2. 用户明确要求稳定性验收、防跑题、防吃设定（任何章数都可提前启用）。
3. 项目已存在 `设定/角色不变量/` 目录（此前启用过，延续执行）。

用户明确说不要稳定性验收时尊重用户，把该偏好按规则沉淀进工作区根 `创作偏好.md`，此后本书不再自动启用（用户改口即恢复）。前 10 章不自动启用的理由：开篇阶段人物与设定尚在成形，边界文件会频繁作废；10 章后主线定型，漂移风险开始超过维护成本。**未启用时本文件所有工件与脚本全部跳过，不阻塞既有流程**；启用后按本文件执行，工件缺失按 FAIL 处理（不静默降级）。

首次启用时的初始化动作：

1. 按 `character-invariants.md` 为主角、主要反派、核心配角建 `设定/角色不变量/{角色名}.md`。
2. 从下一章起，细纲带「稳定性契约」小节（见下）。
3. 已写章节不回溯补契约；审计范围从启用后的第一章开始。

## 工件一：细纲「稳定性契约」小节（写前）

不新建契约文件——把章节契约并入细纲，在 `大纲/细纲_第XXX章.md` 末尾追加：

```md
#### 稳定性契约

##### 必须交付
| 序号 | 情节点 | 功能 | 关键词组 |
|---|---|---|---|
| B1 | {谁做了什么} | {推进/冲突/爽点/伏笔/关系} | {词A、词B} |
| B2 | {谁做了什么} | {功能} | {词A、词B} |

##### 禁止事项
- 不得提前透露：{禁词A、禁词B}
- 不得改变：{既定事实，LLM 门控核对}
- 不得新增：{无 或 列出允许外的禁区}
```

生成规则：

1. **必须交付 beat 从「情节细化」的情节点序列中挑 3-6 个非砍不可的点**（爽点、反转、伏笔埋设/回收、关键信息揭示），不是全部情节点。beat 编号 B1/B2… 连续。
2. **关键词组是本 beat 交付后正文必然出现的 2-4 个具体词**（人名+物件、地点、数字、专名），顿号分隔。脚本逐词在正文里字面匹配，全部命中才算 beat 交付。选词原则同 `character-invariants.md` 的可 grep 规则：`账单、4800` 可验，`真相大白` 不可验。正文润色改写不影响关键词命中——这比"beat 原句必须逐字出现"宽松，专为改稿留余地。
3. **`不得提前透露：` 行是机器验证的禁词**（顿号分隔，正文出现任一即 FAIL，错误码 `Foreshadow_Early_Payoff`）；`不得改变：` / `不得新增：` 由漂移门控的 LLM 审查核对，脚本不判。
4. 契约在开写前落盘；"用户说直接继续写"也不得跳过。回炉重写某章时先改契约再改正文。

## 工件二：漂移门控（写后）

每章正文写完、宣布完成之前，按以下模板把审查结论写入 `追踪/漂移门控/第{N}章.md`：

```md
## Plot Drift Gate：第 N 章

### 结论
- Gate: PASS / FAIL
- 需要修复的 S1/S2：{无 / 列出}

### Findings
| severity | code | evidence | issue | fix |
|---|---|---|---|---|

### Beat 核对
- B1：已交付 — {正文证据句}
- B2：{已交付/缺失} — {证据}

### State Delta（本章改变了什么）
- {角色/能力/关系/资源/信息/时间线变化，一行一条}

### 下一章继承关键词
- 继承关键词：{2-5 个具体词，人名/物件/地点/事件锚点，下一章正文必须出现}

### 修复后复检
- 已修复：
- 用户确认保留：
```

审查顺序（LLM 执行，结论落盘）：

1. 对照细纲稳定性契约核对每个必须 beat（逐个写进「Beat 核对」，脚本会验证每个 B# 编号在门控文件中出现）。
2. 对照当前卷纲核对卷目标推进。
3. 对照 `设定/角色不变量/` 核对动机与认知边界。
4. 对照 `追踪/伏笔.md` 核对提前兑现、遗忘、新增未入账。
5. 对照追踪文件核对状态同步，把本章变化写进 State Delta。
6. 从本章章尾钩子和活跃线索中提炼「继承关键词」——这是对下一章的机器可验承诺，选词按可 grep 规则。

### 错误码表

| code | 默认严重度 | 判定 | 谁判 |
|------|-----------|------|------|
| `Plot_Drift` | S1/S2 | 正文偏离本章核心事件或当前卷目标 | LLM |
| `Beat_Missing` | S1/S2 | 必须 beat 的关键词组未全部出现在正文 | 脚本 |
| `Beat_Compressed` | S2 | 必须 beat 被摘要化，没有写成可感场景 | LLM |
| `Canon_Conflict` | S1 | 与既有设定、时间线、能力限制冲突 | LLM |
| `Motivation_Drift` | S1/S2 | 违反行为红线，或行为缺动机链 | 脚本+LLM |
| `Knowledge_Leak` | S1 | 角色知道了当前不该知道的信息 | 脚本+LLM |
| `Foreshadow_Early_Payoff` | S1/S2 | 禁词提前出现 / 伏笔提前兑现泄底 | 脚本+LLM |
| `Untracked_Addition` | S2 | 新增人物/设定/支线/规则但未入账 | LLM |
| `State_Not_Updated` | S2 | 正文有状态变化但 State Delta / 追踪文件未同步 | 脚本+LLM |
| `Contract_Missing` | S1 | 细纲缺稳定性契约小节 | 脚本 |
| `Gate_Missing` / `Gate_Failed` | S1 | 门控文件缺失 / 结论非 PASS | 脚本 |
| `Handoff_Missing` / `Continuity_Missing` | S1/S2 | 交接包缺失 / 继承关键词未在下一章出现 | 脚本 |

通过规则：有 S1 不得标记章节完成；S2 必须修复或由用户明确确认保留（记入「修复后复检」）；S3/S4 进待修清单，不阻断日更。

## 工件三：章节交接包（门控通过后）

每章门控 `Gate: PASS` 后、进入下一章前，运行：

```bash
node scripts/handoff-pack.js --write {N}
```

脚本从门控（State Delta、继承关键词）、细纲（章尾钩子/结尾设定）、`追踪/伏笔.md`（状态为已埋的活跃行）、`设定/角色不变量/`（本章出场角色）自动汇总，落盘 `追踪/交接包/第{N}章_to_第{N+1}章.md`。**门控非 PASS 时脚本拒绝生成**——失败章节不得交接到下一章，先修复。

交接规则：

1. 下一章开写前先读交接包，再定下一章稳定性契约；继承关键词必须在下一章正文出现（审计脚本验证）。
2. 交接包不是章节摘要，只汇总会影响下一章的状态、钩子、伏笔、角色边界；它不替代追踪文件。
3. 交接包与追踪文件不一致时，先修追踪文件，再重新生成交接包。
4. 回炉改了第 N 章后，必须重写门控并重新生成第 N 章交接包。

## 批量验收：稳定性审计脚本

批量日更写完一批、或回炉复检时运行：

```bash
# 单章
node scripts/stability-audit.js {N} {N}
# 批量 + 报告落盘（追踪/稳定性审计/日更_第{start}章_to_第{end}章.md）
node scripts/stability-audit.js --write {start} {end}
# 自动化/runner 场景
node scripts/stability-audit.js --json {start} {end}
```

逐章检查：细纲稳定性契约存在且有 B# beat、beat 关键词组全部命中正文、禁词未出现、门控存在且 `Gate: PASS`、门控覆盖全部 B#、门控含 State Delta、角色不变量 POV 感知扫描；相邻章检查：交接包存在、其 Gate 为 PASS、继承关键词在下一章正文命中。任一 FAIL 退出码 1，诊断带错误码。

## 修复分派与闭环

审计 FAIL 后按错误码分派（项目已部署对应 agent 时 spawn，否则主线程执行）：

| 错误码 | 分派 | 处理范围 |
|--------|------|---------|
| `Plot_Drift` / `Beat_Compressed` / `Foreshadow_Early_Payoff` | story-architect | 结构裁决：跑题、漏 beat、伏笔提前兑现，先裁定改正文还是改契约 |
| `Motivation_Drift` / `Knowledge_Leak` | character-designer | 角色裁决：动机漂移铺垫、认知泄漏改写或不变量修订 |
| `Beat_Missing` / `Contract_Missing` / `Gate_*` | narrative-writer | 局部正文修补 / 补契约补门控 |
| `State_Not_Updated` / `Untracked_Addition` / `Continuity_Missing` | consistency-checker | 追踪文件复核同步、继承落实 |

闭环：修复 → 重写受影响章节的漂移门控 → 重新生成交接包 → 重跑 `stability-audit.js`，直到 PASS。**审计未 PASS 前不宣布本批完成、不宣布回炉完成。**

## 归档（防长期积累）

门控和交接包每章各一个文件，长篇会持续累积（500 章 ≈ 1000 个）。每完成 50 章或一卷结束时（与 SKILL.md「追踪文件归档」同一时机），运行：

```bash
node scripts/archive-stability.js            # 默认保留最近 20 章活跃窗口
node scripts/archive-stability.js --keep 30  # 自定义窗口大小
node scripts/archive-stability.js --dry-run  # 只报告会移动什么
```

脚本按 `正文/` 最大章号倒推活跃窗口，把窗口外的漂移门控、交接包、审计报告分别移入 `追踪/归档/漂移门控/`、`追踪/归档/交接包/`、`追踪/归档/稳定性审计/`——移动不删除，逐文件保留可回查；窗口首章的入向交接包保持活跃（批量审计的交接继承检查需要它）。

**归档对验收透明**：`stability-audit.js` 和 `handoff-pack.js` 在活跃目录找不到文件时自动回退读 `追踪/归档/` 对应位置——老章节回炉复检不需要先取回文件。回炉重写的新门控/交接包照常写入活跃目录，同名文件以活跃目录为权威（下次归档时新版本覆盖归档里的旧副本）。

## 与既有机制的关系

- 不改变缺失文件回退规则：未启用稳定性时，伏笔/时间线/角色状态缺失照旧不阻塞。
- `check-ai-patterns.js` / `normalize-punctuation.js` / `check-degeneration.js` 管文字质量，本机制管剧情连续性，互不替代，日更 Step 3 依次执行。
- `/story-review` 的全量审查与本机制互补：审计是增量、确定性、每批必跑；story-review 是全量、语义、按需触发。
- **结构化状态库（实验性旁路，references/state-store.md）**：`追踪/状态库/` 分片 JSONL 事件流，补两个本机制覆盖不到的能力——"第 N 章时点的世界状态/角色认知"查询（回炉老章节时替代被覆盖的当前值）和事件流矛盾检测（死亡后活动、伏笔未埋先收）。审计管正文与承诺字面一致，`state-query.js check` 管状态时间线自洽，互不重叠；状态库缺失不阻塞任何流程。
