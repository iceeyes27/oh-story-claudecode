# 規劃章節

## 一、前提

- 上一章必須已完成：`追蹤/場景狀態.md` 中上一章的「收尾」是「已通過」，或上一章已在 `導入/清單.json` 確認且版本相符。
- 未完成就告訴使用者，停止。

## 二、到期檢查

讀 `設定/兌現登記.md`、`追蹤/追蹤.md`、`大綱/大綱.md`，列出：

1. 預定位置已到或已過、還不是「已兌現」的兌現條目
2. 超出窗口的常駐條目
3. 預計回收章已到的伏筆
4. 上一章留下的「下一章承諾」

每一條都要有處置：**排入本章**／**延期**（寫新位置與原因）／**退役**（寫原因）。你可以先提建議，由使用者決定。不能讓任何一條沒有處置就消失。

## 三、細綱草案

依 `大綱/細綱/_模板.md` 寫 `大綱/細綱/第NNN章.md`，檔頭狀態寫「草案」。重點：

- 本章目標：這一章結束時，什麼改變了
- 本章賣點承接：本書核心賣點在這一章由哪個場面讓讀者得到；過渡章也要寫出讀者這章的收穫
- 按視角、時間地點或局面變化拆場景，不固定數量；每個場景寫清楚：視角、時間地點、在場人物、場景目標、阻礙、情節點、結尾狀態、閱讀回報、讀者期待、展開與略寫、字數目標
- 閱讀回報寫成讀者看得到的事件；一個場景說不出閱讀回報，先考慮併入相鄰場景或補一個局面變化，而不是硬湊
- 展開與略寫：列出要在現場寫出過程的時刻，以及讀者已懂、一筆帶過的確認、流程、記數與搬運
- 每個場景的「本場景兌現」表：編號、關係（兌現／部分兌現／鋪墊／涉及）、本場景要呈現什麼
- 情節點寫成「發生了什麼」，不寫「要表現什麼」

## 四、一致性預檢

呼叫 `consistency-checker` 檢查細綱草案（給它細綱、設定、相關角色卡、追蹤、兌現登記）：有沒有違反約束、角色會不會用到他還不知道的資訊、要兌現的條目前置條件是否已滿足。把問題附在草案最後。

## 五、交給使用者確認

在對話中簡短列出：本章目標、本章賣點承接、各場景一句話與閱讀回報、兌現安排、到期檢查的處置、預檢發現的問題。請使用者確認或修改。

## 六、確認之後

使用者明確確認後：

1. 細綱檔頭狀態改為「已確認」。
2. 依 `.claude/workflows/adoption.md` 執行 confirm-plan，登記場景及收尾並綁定細綱版本。
3. `設定/兌現登記.md` 中排入本章的條目狀態改為「已排入」，預定位置寫上章節與場景；延期與退役的條目照使用者決定更新。
4. 是 Git repo 時依 adoption 流程只提交本次檔案，原有暫存不動。
5. 告訴使用者可以用 `/write-scene` 開始寫。
